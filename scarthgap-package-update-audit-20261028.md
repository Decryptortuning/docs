# Scarthgap package maintenance audit — next improvement round

Date: 28 October 2026. Scope: read-only package/source audit while the 5.0.4 metadata-refactor build is running. This report proposes the **next** candidate; it neither changes nor qualifies the current build. No build, test, fetch into a checkout, deployment, hardware access, or source/configuration edit was performed. License analysis is explicitly outside scope.

## Decision

Move the next candidate from the frozen Poky 5.0.4 base to **Yocto 5.0.21 Scarthgap maintenance**, with reviewed matching meta-openembedded and NXP layer revisions. Add an explicit second pass for vendor overrides and project forks: a Poky update alone will leave important selected multimedia and USB recipes behind. Keep Yocto 6, new compiler/Python majors and automatic flight/MCU firmware promotion deferred.

The official [5.0.21 release artifact](https://downloads.yoctoproject.org/releases/yocto/yocto-5.0.21/RELEASENOTES) identifies Poky `4fb7016a07507683359ebd620f1951fd5ea44bfa`, OE-Core `b4f06303e55c7270a8482a610927a1c41d5dbf9c` and BitBake `d3b32587c2314febf96897f97e0172790b4fc1cf`. These are concrete candidate pins, not instructions to change the active checkout. Cached search results still say 5.0.20 or “5.0.21 under review”; the release artifact resolves that discrepancy. Do not infer a September publication date from the release-table label. Scarthgap remains supported through April 2028 according to the [official release table](https://www.yoctoproject.org/development/releases/).

NXP’s [6.6.52-2.2.2 manifest](https://raw.githubusercontent.com/nxp-imx/imx-manifest/imx-linux-scarthgap/imx-6.6.52-2.2.2.xml) still pins Poky `200d12b6a58ad961d60a7774ca0f7a9d29498724` and meta-openembedded `72018ca1b1a471226917e8246e8bbf9a374ccf97`. ## P2: forks, stale dependencies and image contents

NumPy is **1.26.4**, also the 5.0.21 recipe version. Retain it for this round while rebuilding against maintained Python 3.12. A NumPy 2 migration changes extension ABI and deserves a separate coordinated work package. `python3-posix-ipc` is really **1.1.1**, not the legacy 0.9.9 recipe also present on disk; meta-openembedded Scarthgap offers **1.2.0**. Qualify semaphore/shared-memory naming, ownership, timeout and cleanup semantics before promotion. `python3-monotonic` is **0.6**: replace its consumers with Python’s `time.monotonic()` and then remove the dependency, rather than merely bumping it. The [project documentation](https://pypi.org/project/monotonic/) confirms modern Python already supplies the implementation.

PyMAVlink’s installed `1.1.56+git…3887c3f7b4` is an owned Solo dialect fork; DroneKit 2.4.0 is pinned to `9b1fa763…`, DroneKit-Solo 1.2.0 to `5d53ef72…`. [DroneKit upstream](https://github.com/dronekit/dronekit-python) explicitly seeks maintainers. Treat these as owned maintenance liabilities: document exported APIs, dialect generation, byte order/CRC, message IDs and listener/thread behavior; selectively backport fixes. Do not replace them blindly with newest PyPI packages. ShotManager, SoloLink, sololink-python and stm32loader require coordinated producer/consumer review, not unrelated version chasing.

Current integration pins are supplied separately from old-image versions. In particular the preserved controller has SoloLink `46d677af01`, whereas current source pins select `74e468149e4f`; this is expected epoch drift, not a package-update recommendation. The chosen prebuilt artoo `60a2707…` remains intentional; development firmware `4803457…` is not promoted. Pixhawk stock/green and gimbal payloads likewise require separate hardware/protocol qualification.

NXP `imx-codec` 4.9.0, `imx-parser` 4.9.2, imx-gst plugin 4.9.2, VPU 5.4.39.3, GPU/G2D 6.4.11.p2.10, firmware-imx 8.26 and linux-firmware 20240909 should move only as a reviewed vendor-compatible bundle or targeted firmware subset. Newer i.MX8/9 releases do not establish i.MX6 ARMv7 compatibility. No complete vendor binary advisory coverage was established here.

The old drone image still includes BlueZ, oFono, neard, rpcbind and NXP WLAN extras. Current source policy already removes several unused feature families for both roles; compare the new manifest before filing duplicate cleanup. Similarly examine broad GStreamer plugin groups, package managers, locales and Python’s full modules/ensurepip against actual development/release needs. Preserve recovery tools. Main-image tar/gzip behavior may come from BusyBox, not standalone GNU package names; native tar and any standalone gzip need their own maintenance checks. An old package is not automatically unused or insecure.

## Next-round work packages and frozen gate

1. **Freeze baseline evidence:** preserve current refactor receipts when its build finishes; collect C/D main/initramfs manifests and later both release-profile manifests. Keep these separate from the historical inventory above. Record exact image hashes and source/profile identity.
2. **Prepare one coherent maintenance candidate:** review Poky 5.0.21, compatible Scarthgap meta-openembedded (observed branch `2db6aece32c7…` is a review starting point), NXP 2.2.2 deltas and all custom appends/provider preferences. Pin complete commits and downloads. Inventory changed versions **and** patch-only changes. Review rsync 3.5.1 and Python 3.12.16 as explicit additions beyond the tag.
3. **Resolve vendor and fork exceptions:** rebase kernel/U-Boot/local DT/config patches; reconcile GStreamer/FFmpeg security fixes with NXP acceleration; remove the libusb override when qualified; decide minimal package subsets and owned Python maintenance. Set an owner and rationale for every retained exception.
4. **Complete the combined source gate before testing:** wait for related edits to settle, pin the combined candidate, then review actual boot/recovery scripts, image packaging, source/profile provenance, network pairing, application interfaces, MCU selection and media consumers together. Do not start builds/tests while this source set moves. This is the AGENTS sequencing requirement, not a new approval request.
5. **Build and qualify only that frozen candidate:** separate TMPDIR/profile outputs; check manifests, selected providers, native tools and ABI as well as package versions. Run CVE assessment with a dated database and patch/config disposition evidence, then targeted offline tests and both-board boot/recovery/network/video/USB/serial qualification. Re-run only tests affected by subsequent fixes after freezing a replacement candidate. Do not claim new packages fix the unresolved live GPIO/STM32 reset issue.

Completion of this audit means the next maintenance work is identified and inventory is reviewable. It does not make a new image release-ready, certify all packages, or authorize changes to the active build.
