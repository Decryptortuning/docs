# Artoo STM32 source, dependency, and modernization audit — 2026-10-28

The best next investment is to repair bounded protocol handling, persistent-parameter failure handling, and interrupt/time ownership before changing the firmware architecture. The current source already builds with GCC 13.2. A wholesale HAL, RTOS, graphics, or MAVLink replacement would add substantial compatibility work while only 15,352 bytes of application flash remain.

This is a static audit and staged implementation backlog. It is not a hardware qualification, a completed modernization, or authorization to program a controller. No firmware source, build input, pin, generated asset, or target was changed for this audit. No firmware build, test execution, serial open, probe connection, SSH action, reset, or flash operation was performed. The only authored artifact is this report.

Subsequent authorized implementation and current evidence are tracked in [the resolution ledger](artoo-modernization-resolution-20261028.md). The findings below remain the historical audit of `60a2707`, not a claim that the repaired defects persist in the latest local candidate.

## Findings and prioritization

“Confirmed” means the current source contains the described behavior; it does not mean the failure was reproduced on this physical controller. “Candidate” identifies a plausible failure requiring a focused reproducer, measurement, or peer/board evidence. Priority P1 means repair before accepting a modernization candidate on hardware; P2 means the next planned reliability or maintenance wave; P3 means latent/unused support cleanup. Cost descriptions are estimates, not measured deltas.

### A01 — P1, confirmed: SLIP storage and appends are not bounded

[`HostProtocol::Packet`](/home/jresp/Active_GH/artoo-firmware/src/hostprotocol.h:60) uses `PacketBuffer<MAVLINK_MAX_PACKET_LEN>` for both raw receive data and encoded transmit data. That constant is 263 for the current MAVLink 1 dependency. [`PacketBuffer`](/home/jresp/Active_GH/artoo-firmware/src/packetbuffer.h:56) writes without a runtime capacity check; its assertions disappear in production. `isFull()` tests equality, so it cannot contain an already-overrun length.

One full 263-byte MAVLink frame needs another byte for the host message ID on receive, and up to `2 + 1 + 2*263 = 529` bytes when SLIP encoded for transmit. Existing outgoing flight commands are shorter, so this maximum is not a claim that every current command overruns. There is also an existing path: the 172-byte `StoredValues` response can require up to 347 encoded bytes. Configuration handlers accept enough arbitrary bytes to exceed the 263-byte buffer. [`produceHostProtocolPacket()`](/home/jresp/Active_GH/artoo-firmware/src/hostprotocol.cpp:161) sends that structure without an encoded-size check.

Use separate raw and encoded capacities, checked append operations returning success/failure, and frame-level all-or-nothing admission. Preserve the current host protocol bytes. Budget the aggregate output of `Inputs::producePacket()`, which may concatenate several frames, rather than checking only individual packet types. A 529-byte TX buffer instead of 263 costs 266 bytes before padding; a full MAVLink-1 raw host envelope needs at least 264 bytes. A larger buffer alone does not fix unchecked producers or future changes.

Validation: all byte values, all-END/all-ESC payloads, exact-capacity and one-over cases, stored-parameter responses, and aggregate input packets under ASan/UBSan. Check that rejection leaves DMA state and the following frame intact.

### A02 — P1, confirmed: button payload bypasses SLIP escaping

[`ButtonManager::producePacket()`](/home/jresp/Active_GH/artoo-firmware/src/buttonmanager.cpp:289) calls `p.append(be.bytes, sizeof be)` between SLIP delimiters. The all-buttons mask is real binary data: Preset1 and Preset2 are bits 6 and 7, yielding `0xc0`, the END delimiter. Other combinations can yield `0xdb`, the escape byte. Such events can split or corrupt their frame.

Use the same bounded SLIP encoder as other payloads. This is a small code change with no persistent-layout change and negligible expected storage cost. Test round-trip preservation for every 9-button mask and every event type, including simultaneous camera presets. Verify the Linux decoder's existing contract without changing event numbering.

### A03 — P1, confirmed: received payload lengths and strings are inconsistently enforced

[`processPacket()`](/home/jresp/Active_GH/artoo-firmware/src/hostprotocol.cpp:295) contains several independent cases:

- `SetRawIo` reads `bytes[1]` even with no payload. This can read a stale byte inside the packet storage; it is not necessarily an allocation-boundary overread.
- `ButtonFunctionCfg` accepts 5–23 bytes but [`setButtonFunction()`](/home/jresp/Active_GH/artoo-firmware/src/buttonmanager.cpp:90) copies the entire 24-byte structure. The descriptor is not forcibly terminated. Short input therefore imports stale tail bytes, and an unterminated descriptor can escape its own storage when rendered.
- `SetShotInfo` discards the provided length before string comparisons/copies in the gimbal and top-bar paths. The top-bar's 21-byte globally initialized destination retains its final zero byte, so its own destination is not the demonstrated unterminated buffer; the defect is reading beyond the logical payload and accepting stale suffixes.
- [`VehicleConnector::onPairingRequest()`](/home/jresp/Active_GH/artoo-firmware/src/vehicleconnector.cpp:34) copies `sizeof(deviceID)` regardless of received length and only forces termination when `len >= sizeof(deviceID)`. A short unterminated request can copy stale data without a terminator, followed by `strlen()` during confirmation. Pair-result comparison similarly disregards the logical payload extent.
- An oversized received frame is truncated to the buffer and still dispatched at END. RX ring overflow drops bytes without establishing a full discard-until-END recovery state. This can interpret a prefix or damaged frame as valid input.

Introduce a table of exact/minimum/maximum lengths and explicit bounded string contracts. Reject malformed frames as a whole, zero-initialize local decode structures, and publish only validated complete values. Keep truncation policy explicit for user-visible labels. This should add modest code and a small error counter/state flag; no heap is needed. Test empty, partial, embedded-NUL, maximum, oversized, dangling-escape, dropped-byte, and back-to-back recovery cases for every message ID.

### A04 — P1, confirmed: parameter save can lose failure state and leave flash unlocked

[`Params::periodicWork()`](/home/jresp/Active_GH/artoo-firmware/src/params.cpp:59) clears `dirty` even when `save()` fails. Erase and programming error returns skip `McuFlash::lock()`. [`endProgramming()`](/home/jresp/Active_GH/artoo-firmware/src/stm32/mcuflash.h:99) discards the final operation's status; `programHalfWord()` checks the preceding operation, then initiates the next one. The final halfword's failure can consequently be missed. There is no readback of the completed structure.

First preserve the existing 172-byte on-flash layout: lock on every exit, propagate final status, read back, retain dirty state on failure, and retry with an explicit policy. Snapshot values before programming so ISR writers cannot mutate the saved record midway. Keep the armed-flight restriction and add tests for every failed erase/program position. Expected cost is small code plus a possible 172-byte snapshot.

The larger design gap is a single erased-and-rewritten parameter page without checksum, schema, sequence, or atomic commit. Any non-`0xffff` word is treated as initialized; a torn page can be accepted as calibration. A CRC/versioned record and migration require coordination with Linux backup/restore and page preservation. Multiple records in one page still lose power safety during compaction. A two-page scheme reduces application space by another 2,048 bytes, leaving 13,304 bytes relative to the present binary, and needs a coordinated linker/updater transition. Do not silently move the current parameter address or repurpose flash before that transition is designed.

### A05 — P1, confirmed: parameter “validity” does not establish usable control values

[`StickCalibration::isValid()`](/home/jresp/Active_GH/artoo-firmware/src/params.h:27) checks only whether storage is erased. [`StickAxis::setCalibration()`](/home/jresp/Active_GH/artoo-firmware/src/stickaxis.cpp:63) then accepts the values. Equal/reversed extrema or trim outside the usable range can create zero/invalid scale denominators, dead-zone wrap, non-finite results, or invalid float-to-integer conversions. Sweep seconds are multiplied by 1,000 without range/ordering validation; preset floats need finite/range checks; axis mapping accepts individually in-range inputs without establishing an allowed mapping for flight and gimbal roles.

Validate the entire incoming configuration before publishing it: ADC domain, ordered endpoints and axis-specific dead-zone room, bounded sweep interval, finite camera positions, valid enums and allowed stick mappings. Preserve documented alternate stick modes. Invalid input must retain the last valid configuration and produce a defined error, not silently recalibrate during flight. `-ffast-math` can invalidate naïve non-finite checks; validate float bit patterns or compile validation with appropriate floating-point semantics, then evaluate removal of that flag separately. Firmware validation remains necessary even with the fixed Linux updater's calibration checks.

Cost: modest branch/code increase and possibly one staged configuration object; no new framework. Test all six axes, alternate modes, erased/partial storage, equal and reversed extrema, dead-zone boundaries, NaN/Inf bit patterns, and sweep overflow. Publish the accepted configuration under the ISR ownership scheme in A07.

### A06 — P1, confirmed: the timebase is not a coherent ISR-safe snapshot

[`SysTime::now()`](/home/jresp/Active_GH/artoo-firmware/src/stm32/systime.cpp:62) reads the fractional hardware counter and then a plain 64-bit `tickBase`, while SysTick updates that base. A rollover between reads can combine different periods. A Cortex-M3 does not make arbitrary 64-bit C++ loads/stores atomic. The plain `lastTick` correction is shared too. Its comment says it is not used in interrupt context, but button handling, LCD TE, and invalid-stick reporting call `now()` from interrupt paths.

Replace this with a documented coherent snapshot that handles a pending SysTick rollover, restores the caller's interrupt mask, and does not use a non-lock-free 64-bit atomic inside an ISR. Options include a short PRIMASK-preserving critical section with a verified counter/pending-bit algorithm, or a naturally sized tick counter plus carefully specified wrap arithmetic. Merely adding `volatile` does not solve consistency or multiple writers. Flash stalls can collapse multiple SysTick periods into one pending interrupt; a monotonic-read repair alone cannot recover unobserved elapsed periods.

Test simulated interleavings immediately before/after rollover, nested callers, wrap, and blocked ticks. Measure real elapsed-time behavior later for button holds, shutdown, haptic durations, link timeout, and camera timing. Expected cost is small state/code, but timing risk is higher than the size suggests.

### A07 — P1, confirmed race opportunities: shared application state needs explicit ownership

[`Ui::pendEvent()`](/home/jresp/Active_GH/artoo-firmware/src/ui.h:57) is called from foreground and ISR paths. [`RingBuffer::enqueue()`](/home/jresp/Active_GH/artoo-firmware/src/ringbuffer.h:68) is a plain read/write tail sequence. An interrupt can publish to the same tail while foreground is interrupted, losing an event. The UART RX ring is structurally single-producer/single-consumer, but ordinary indices do not provide an explicit compiler publication contract. Neither case is repaired just by declaring an entire object volatile.

Inventory and specify ownership for the event queues, button timestamps/event masks, haptic pattern/deadline, battery samples, input mapping/calibration, invalid-stick snapshot, host request/TX state, and flight command union. Some are compound or 64-bit values. The invalid-stick record's flag is published before its fields, which is the wrong order if another context can consume it. Parameter/configuration updates can interrupt ADC use midway.

[`HostProtocol::requestTransaction()`](/home/jresp/Active_GH/artoo-firmware/src/hostprotocol.cpp:77) masks only the TX DMA IRQ and then unconditionally enables it; it does not restore previous enable state. Packet production also runs directly from the DMA callback and request callers, including button interrupt paths. Encoding, floating-point work, and multiple shared producers therefore occur in contexts that are easy to overlook.

Prefer short ISRs that capture samples/status and schedule work; give encoding and application transitions a single foreground owner. Where immediate work is required, use small mask-preserving critical sections or proven lock-free 32-bit publication. Keep DMA buffers stable through completion. Do not change NVIC priorities until this ownership is explicit; currently default priorities can hide assumptions about nesting. Tests should force interleavings at queue/snapshot boundaries; later measure interrupt latency and UART loss under UI, ADC, button, and flash activity. Cost ranges from a few bytes of state to additional bounded queues; measure each step rather than introducing an RTOS.

### A08 — P1, confirmed: shutdown does not disable the requested button interrupts

[`Button::disableIRQ()`](/home/jresp/Active_GH/artoo-firmware/src/button.h:173) calls `pin.irqEnable()`. The shutdown list also repeats Preset1/Fly and omits Preset2. Repair the helper and express the non-power-button shutdown set once. Validate the EXTI mask with mocked registers and later the intended physical power-button wake behavior. The change should have negligible memory cost; it must not disturb the power wake pin.

### A09 — P1, confirmed: DMA errors are delivered as normal completions

[`Adc::dmaCallback()`](/home/jresp/Active_GH/artoo-firmware/src/stm32/adc.cpp:151) has an empty error-handling branch and still invokes sample completion. [`Usart::dmaTXCallback()` and `dmaRXCallback()`](/home/jresp/Active_GH/artoo-firmware/src/stm32/usart.cpp:140) ignore flags. The SPI callback detects transfer error but has no recovery/reporting. A transfer error can therefore publish stale/partial data or advance transmission as though successful.

Distinguish TCIF from TEIF, stop/reset affected channels, count errors, and define retry/drop behavior without repeating a vehicle command unintentionally. Do not publish incomplete ADC samples as fresh controls or battery readings. First test flag combinations and register transitions; later induce or simulate hardware error paths with a recovery acceptance plan. Expected cost is small counters/state and code.

### A10 — P1, confirmed: command ACK identity uses incompatible number spaces

[`FlightManager` ACK handling](/home/jresp/Active_GH/artoo-firmware/src/flightmanager.cpp:484) compares wire `ack.command` with local `Command::ID`. For example, local SetArmState is 2 but emitted `MAV_CMD_COMPONENT_ARM_DISARM` is 400; local Takeoff is 4 while emitted `MAV_CMD_NAV_TAKEOFF` is 22. Normal ACKs therefore do not mark the command slot complete through this match. `cmdAcknowledged()` still executes afterward, so this finding does not mean that all ACK-specific UI/takeoff handling is skipped. The command slot can also be overwritten, and the production-disabled assertion is the only pending-slot guard.

Store explicit wire identity and expected response type alongside local operation/state. Define bounded completion/timeout behavior and intentional replacement policy. SET_MODE and mission requests have different legacy response conventions; preserve compatibility with the actual Solo/Pixhawk peers and custom SOLO button commands. Do not add blind automatic retries to arm/takeoff operations. Test accepted/rejected/unrelated/late ACKs, mode telemetry, disconnection, and simultaneous requests. Memory cost is a few state fields unless a queue is deliberately justified.

### A11 — P1/P2, confirmed behavior with hardware-dependent impact: battery error handling and alert ordering

[`Battery::onCellSamples()`](/home/jresp/Active_GH/artoo-firmware/src/battery.cpp:86) subtracts bottom from unsigned 16-bit top. An invalid sample with top below bottom wraps to a large upper-cell value. The overvoltage branch keeps charging disabled, but skips the ordinary undervoltage shutdown branch. Reject inconsistent measurements explicitly and choose a documented invalid-sensor state. An all-zero sample also merits a startup test because level initialization is conditional on the cell sum changing.

[`updateBattLevel()`](/home/jresp/Active_GH/artoo-firmware/src/battery.cpp:166) calls `onLevelChanged(newLevel)` before assigning `battLevel`; the latter checks `uiLevel()` derived from the old level. Critical/failsafe decisions can lag an accepted level transition. Compute decisions from the new snapshot consistently. The existing raw-vs-displayed percentage thresholds need an explicit truth table before changing them.

These arithmetic/ordering repairs are small. Charging thresholds, thermistor conversion, pack-ID policy, balancing duty, and empirical ADC scaling must retain current values until evaluated with the actual battery/board. BB03 and DVT differ in thermistor/ID wiring. Unknown/disconnected thermistor and battery-ID cases require acceptance tests; source inspection alone cannot certify charging safety.

### A12 — P1/P2, confirmed: factory functions remain callable in production firmware

Host messages can reach GPIO/output tests and self-test. GPIO testing can drive charging controls directly, and self-test reconfigures LCD/ADC pins without a complete restore of their prior configuration. Self-test has a magic value and connection check, but these are not a separate factory build/profile boundary.

Make destructive fixture operations explicitly unavailable in the production profile or require a separate, documented physical factory mode. Preserve manufacturing capability in its own build. This is a host-protocol trust-boundary finding, not a claim of a demonstrated remote exploit. Removing unused production handlers may save flash; size and factory requirements must be measured/reviewed first.

### A13 — P2: startup, fault handling, linker, and stack need machine-checked contracts

The custom startup selects 12 MHz HSE ×6, 72 MHz AHB/APB2, 36 MHz APB1, and 12 MHz ADC; comments still describe 36 MHz AHB/APB2. Oscillator/PLL and several peripheral waits are unbounded. Fault handlers spin indefinitely; the default unexpected IRQ handler returns without identifying or masking its source. No active independent/window watchdog policy was found.

The linker collects only `.init_array`, not priority-suffixed `.init_array.*` or preinitializers, and discards every `.ARM.*` section, including useful ABI attributes. It has no explicit heap/stack boundary symbols, stack reservation assertion, retained crash area, or automated constructor count/content validation. Its FLASH region already excludes the parameter page, which is useful protection and must be retained.

Add a post-link checker for loadable flash extents including initialized data, vector placement/alignment, Thumb reset, RAM bounds, unexpected sections/runtime imports, constructors, and reserved parameter space. Add linker assertions and explicit supported runtime sections; do not enable exception unwinding as a side effect. Capture `-fstack-usage` and a call/ISR nesting budget; runtime watermark/canary checks require a later hardware candidate. A minimal retained fault record may use backup registers or a reserved `.noinit` area after reset-path review.

Timeouts need a usable clock at each startup phase and a defined safe output/failure policy. A watchdog reset also affects controller power rails, i.MX startup, UART ownership, and charger operation. Do not simply enable IWDG and regard the device as recovered. Its introduction requires a system recovery design and separately authorized hardware acceptance.

### A14 — P2: scheduling and control timing need measurement before redesign

The cooperative task mask intentionally coalesces events. It cannot count missed 50 Hz ticks. Host RX drains its ring without a fixed work quota; button/haptic tasks can reschedule immediately. A sustained producer or long UI/flash operation may delay periodic work. Camera code assumes a fixed 20 ms interval, and heartbeat-counted link/state timeouts stretch if ticks are coalesced. The main-loop work-check/WFI transition also merits an interrupt-interleaving test; the next SysTick bounds the usual sleep delay, but that is not a general wakeup proof.

Add bounded work quotas and low-cost timing/overrun counters first. Convert selected deadlines to elapsed time only after A06, preserving current control outputs under nominal timing. Test camera preset/tween curves, manual override, gimbal feedback, DSM channel mapping, GPS/home distance, SmartRTL, lockout, kill-button combination, arming/takeoff, and loss/recovery state machines. Do not retune expo, filters, thresholds, or force-disarm behavior in the same patch as compiler or protocol changes.

### A15 — P2/P3: graphics and asset contracts have several unguarded edges

Compiled image/font streams are trusted at runtime: RLE uses sentinel termination without an encoded-length/pixel-count bound, palette bounds rely on disabled assertions, and rectangle/string placement is not generally clipped. This is primarily an asset-generation validation opportunity with zero target RAM cost. Validate every generated stream's decode length, palette indices, dimensions, glyph widths/heights, and target integer limits; produce a contact sheet/golden raster for all assets and fonts.

There is also a concrete string-loop defect in [`Gfx::writeCanvasCenterJustified()`](/home/jresp/Active_GH/artoo-firmware/src/gfx.cpp:259): the newline branch increments `s`, and the loop increments it again. A final newline can advance beyond the terminating NUL; consecutive newlines are mishandled. Add bounded text fixtures including empty strings, consecutive/final newlines, missing glyphs, and overwide labels. Test zero-width/height rectangles before adjusting LCD address-window arithmetic.

The recent Pillow `getsize` to `getbbox` adaptation deliberately retains the former top-bearing-inclusive height. New font bearings or FreeType versions can still alter glyph geometry and compressed data. Keep font files, rendering-library identity, palette order, and all raster golden results in the build provenance. Do not replace the LCD driver or install a new GUI library to solve these small issues.

### A16 — P3, confirmed latent support defects and maintenance candidates

- `ISR_DMA2_Channel4_5` dispatches only channel 4's handler, leaving channel 5 unserved. Current principal ADC1/UART1 paths use DMA1, so this is not evidence of the active controller losing DMA2 interrupts.
- Complementary timer helpers use `ch-1 * 4` rather than `(ch-1)*4`; TIM8 is recognized as advanced but omitted from timer clock-enable initialization. Verify call reachability before prioritizing these over active paths.
- NVIC priority helpers OR a new byte into the old priority, so they cannot reliably lower/replace a previously set priority. No active priority customization was found.
- DMA channel registration has no general argument-range contract; duplicate registration returns null and callers need a defined failure path. UART4/5, ADC3, SPI, FSMC, and unused peripheral variants need exact-part register/DMA mapping review before claiming support.
- Generic rotate-by-zero, absolute-value minimum integer, moving-average intermediate multiplication, and telemetry-dependent shifts deserve UBSan/property tests. Current call ranges can make individual cases unreachable; do not label every generic edge as a current field failure.
- BB02 still appears selectable but has obsolete pin names and conditional battery/TE assumptions inconsistent with current unconditional callers. Treat it as unqualified, not a supported build matrix entry. BB03 and DVT need distinct pin/behavior fixtures. The reported hardware revision is the compile-time BOARD value, not independent silicon/PCB identification.

## Build, ABI, memory, and dependency modernization

### Current build and runtime choices

The qualified WSL baseline uses Ubuntu 24.04 native Linux tools: GCC Arm 13.2.1 (`gcc-arm-none-eabi` package `15:13.2.rel1-2`), binutils 2.42, newlib 4.4.0.20231231, Tup 0.7.11, Python 3.12.3, and Pillow 10.2.0. Installed supporting tools include CMake 3.28.3, Ninja 1.11.1, and gdb-multiarch 15.1. Package revisions should accompany future receipts because distribution patches matter.

`Tupfile` uses C++11, `-Os`, section garbage collection, `-ffast-math`, Cortex-M3 Thumb/software floating point, and disables exceptions, RTTI, and thread-safe local-static initialization. It links through the GCC driver with custom startup, nano.specs, libc/libm/libgcc/libnosys; normal firmware does not link the full C++ standard runtime. Semihosting is a distinct alternate configuration. Existing Python asset compatibility, packed-MAVLink CRC alignment repair, intentional fallthrough annotations, and repeatable standalone Tup wrapper are already completed work.

The mandatory `-u _printf_float` is a specific space-recovery candidate. The existing ELF contains `_printf_float` (1,348 bytes) and `_dtoa_r` (3,764 bytes); active owned formatting calls inspected use integer/string formats. Remove the forced float-format import in an isolated comparison only after checking every reachable format. Do not add those two symbol sizes and claim the entire sum as guaranteed savings: library reachability and shared helpers determine the actual delta. The map also includes malloc/free/reentrant newlib and libnosys `_sbrk`; absence of an explicit application `malloc` is not proof of no heap use.

Choose an explicit runtime policy: prove allocation is absent and fail any unexpected allocation, or provide bounded `_sbrk` with a reserved heap and stack guard. Define syscall failures/termination deliberately, and keep diagnostics visible until implemented. Do not hide the current libnosys warnings with linker-warning suppression. Review library calls from ISR paths for reentrancy, large stack frames, and latency. The ELF also contains large software math routines such as `__ieee754_pow` and `__kernel_rem_pio2`; narrower float operations or lookup/fixed-point alternatives are experiments requiring numerical/output comparisons, not automatic substitutions.

Keep C++11 for the first reliability patches. A separate C++17 step can improve type-safe constants, `static_assert`, bounded array APIs, explicit state types, and compile-time validation without heap/RTTI/exceptions. A C++20/23 standard switch alone supplies little benefit here. Do not assume `std::atomic<uint64_t>` is lock-free, or introduce allocating strings/containers, general formatting libraries, or hidden local-static guards. Assess LTO only after undefined behavior and section/constructor contracts are repaired; optimization can expose existing races and alter size, timing, debug visibility, and startup retention.

### MAVLink provenance and compatibility

The checked-in v1 library carries generated version metadata from 2015-11-03. `ardupilotmega` and `common` are included; the source also depends on Solo-specific commands, gimbal behavior, legacy mode/ACK conventions, and an application-specific EKF interpretation. The generator script refers to a sibling `mavlink-solo` checkout but does not lock the XML/generator revision. It also contains a literal `ARTOODIR` removal path instead of variable expansion and uses `pushd` under `/bin/sh`. Do not run it against the active headers as a discovery step.

Recover the exact XML provenance first, record the local aligned-CRC patch, and generate into a separate directory. Compare message IDs, ordered wire fields, lengths, CRC_EXTRA, enums, sender/component IDs, sequence handling, and every used pack/decode operation. MAVLink's [generation guide](https://mavlink.io/en/getting_started/generate_libraries.html) and [serialization specification](https://mavlink.io/en/guide/serialization.html) are the relevant contracts. A v2-capable parser can still transmit v1, but that choice and every peer's accepted envelope need explicit tests. Do not enable signing or change payload framing merely by accepting newer generated headers.

Existing host tests cover the repaired checksum on deliberately unaligned storage and an independent heartbeat wire fixture, including the `123456789` CRC result `0x6f91`. That is valuable but does not cover the full parser, malformed lengths, all used messages, custom commands, or cross-peer state behavior. Add independent fixtures from the locked Linux/Pixhawk/ShotManager dialects rather than only encoder/decoder round-trips from the same generated code.

## Validation strategy and boundaries

Host testing should isolate pure logic behind narrow adapters for clock, registers, flash, and packet transport. Use ASan/UBSan and bounded fuzz/property tests for packet/SLIP/text/calibration; model flash failures and clock interleavings deterministically. Use static analysis from the actual cross compile commands for truncation, shifts, alignment, uninitialized state, bounds, and ISR-call graphs. Start warnings such as conversion/double-promotion/stack-frame diagnostics in a report profile and fix signal-bearing cases; do not bury the maintained warning-as-error build in broad suppressions. Generated/vendor code and owned code should have separate diagnostic ownership.

QEMU is useful for selected instruction/startup experiments, but its official [STM32 board documentation](https://www.qemu.org/docs/master/system/arm/stm32.html) identifies an F100-based `stm32vldiscovery`, not this Artoo F103 board, and lists missing peripherals. It is not a ready-made Artoo simulator or evidence that DMA, charging, LCD, flash persistence, or power sequencing works. A custom emulator/board model is substantial additional work; host fixtures are the first practical step. No emulation was run in this phase.

When hardware work is explicitly authorized later, acceptance must include all six calibrated inputs and alternate mappings, normal/held/simultaneous buttons, SLIP/UART stress with Linux ownership intact, display and all glyphs, camera motion, link loss/recovery, startup/shutdown/backpower behavior, battery/charger/thermal and invalid-sample conditions, flash-save failures, and stack/timing measurement under combined load. Use a controlled bench with vehicle outputs made safe, and preserve known-good firmware/calibration/rollback artifacts. Actual ROM-loader access is `/dev/ttymxc1` at 115200 8E1 with BOOT GPIO45/reset GPIO46; the running Linux service owns the same UART at 115200 8N1/SLIP. These are distinct modes and must not be accessed concurrently. This audit did not open either mode.

A candidate is software-ready only when it has reproducible provenance, preserved wire/layout contracts or a deliberate migration, passing targeted regressions, measured flash/static RAM/stack budgets, and reviewed runtime changes. Hardware-ready and field-ready remain separate claims requiring the corresponding evidence. Local OpenSolo 5 branding supplies none of that evidence by itself.
