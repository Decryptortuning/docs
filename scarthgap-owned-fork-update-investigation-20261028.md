## Concrete PyMAVLink update experiment

The source comparison also found an immediate consumer mismatch: the selected DroneKit heartbeat listener calls `self._handler.master.probably_vehicle_heartbeat(msg)`, but the selected old PyMAVLink `mavutil.py` has no such method. Matching DroneKit to upstream does not establish compatibility with its installed dependencies; its `setup.py` actually declares `pymavlink>=2.2.20`. This is an active downstream dependency exception, not a satisfied upstream version requirement. Astra is preparing a focused compatible helper backport and actual-module heartbeat regression before the maintenance-A freeze. The exact modern helper additionally mentions `MAV_TYPE_ADSB`, which is absent from the legacy enum, so a verbatim copy is insufficient. Review remaining actual caller APIs and retain the full dependency exception in the ledger; a focused backport is not proof of complete modern PyMAVLink equivalence.

Modern PyMAVLink can still generate/use MAVLink 1. A Python library version beginning with 2 does not require changing the wire protocol or flight-controller firmware. The required compatibility work is preserving the existing Solo dialect and callers.

The static XML differences are:

- ID 61, `ATTITUDE_QUATERNION_COV`: old 32-bit `time_boot_ms` becomes 64-bit `time_usec`.
- IDs 63 and 64, global/local position covariance: old time fields and layouts differ from current definitions.
- ID 149, `LANDING_TARGET`: the base field layout differs.
- ID 225: old `GPS_ACCURACY` collides with current `EFI_STATUS`.

The complete field signatures and explicit enum changes are in `mavlink-xml-comparison.json`. This compares declared types/names and stable size-sorted base-field order. It does **not** execute generators, compute/validate generated CRCs, establish message reachability, or prove runtime interoperability. New extension fields alone were excluded from base-signature comparisons.

Prepare an isolated candidate using the verified 2.4.50 source archive, an explicitly owned copy of the authoritative legacy XML include closure, and deterministic generation of the intended MAVLink-1 dialect. Avoid including both conflicting old and modern definitions. Preserve existing imported module paths or update every owned caller together: gimbal helpers import `pymavlink.dialects.v10.ardupilotmega` directly, so an environment variable alone cannot select a replacement dialect for all callers. Include the C headers used by SoloLink and the actual Pixhawk/GoPro message definitions in the contract review.

After the combined source freeze, compare generated message IDs, field order/length, CRC extras, enum values, and independent golden frames against saved firmware/C-header contracts. Exercise actual DroneKit/DroneKit-Solo/ShotManager construction, parameter and mission APIs, GoPro/gimbal requests, heartbeat/timeout handling, stream fragmentation/bad CRC/reconnect and numeric/byte semantics. Generation or replay success is not flight/hardware acceptance. No firmware update is needed merely to begin these offline experiments.

The 2.4.50 distribution declares `lxml` and `fastcrc`. Its `mavcrc.py` actually has a Python CRC fallback when fastcrc cannot import. `fastcrc` upstream is Rust-based. Therefore either cross-package a pinned Rust implementation, or deliberately validate the included fallback and ARM CPU/throughput; Rust is not an unavoidable runtime blocker. The current old recipe already disables its old C mavnative extension. Review generator-only versus runtime XML dependencies explicitly instead of silently dropping package requirements. Keep modern MAVProxy optional and dependent on this dialect decision.

## Owned compatibility patches selected after the upstream comparison

Preserve the owner's prior Python3 fork work and the source9 source pins. Byte identity with upstream DroneKit does not imply that its older Solo PyMAVLink dependency supplies every API. The integration source review found and repaired source-component propagation, vehicle-heartbeat filtering (including cached transport state), and generated char-array text semantics, plus the Python3 bad-CRC exception representation. DroneKit's old clock/future shims are replaced with stdlib equivalents. These are owned-layer patches against the exact existing fork, not a dialect/source replacement.

The upstream setup requirement `pymavlink>=2.2.20` is still a deliberate downstream compatibility exception; a bounded helper backport does not satisfy the entire advertised API. `dronekit-legacy-api-review.json` records the static method/constant review. `tests/runtime/test_dronekit_legacy.py` exercises actual candidate libraries, legacy-generated frames and DroneKit/SoloVehicle producer/consumer paths after the source gate. It includes independent heartbeat CRC/layout, constructor component IDs, rejected heartbeat cache/target/motor state, parameter keys/deadlines, NUL/nonASCII wire preservation, corrupted/fragmented stream handling, GoPro listeners and gimbal/request encoding. Only socket/FD boundaries are replaced; no live flight command is emitted. Broader modern-library migration remains the concrete experiment above, with no claim of full API, ARM or hardware acceptance from these source changes.
